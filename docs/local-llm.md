# Локальная нейросеть для «Грифа» — T-029

Режим предназначен для обработки документов в контуре организации, в том числе
документов с персональными данными в контексте 152-ФЗ. Нейросетевая проверка
выполняется локальной моделью `qwen2.5:3b` на CPU через Ollama. Найденные ПДн
по-прежнему маскируются **до** вызова модели: `[PERSON_1]`, `[PHONE_1]` и т. п.
Исходный документ и его текст не отправляются облачному провайдеру.

Сервис использует фиксированный образ `ollama/ollama:0.13.5` и профиль
`local-llm`. Порт 11434 не публикуется на компьютере; API и Celery worker
обращаются к `http://ollama:11434/v1` внутри общей сети Compose. Определения
API и worker не изменены. Без профиля новый сервис не запускается.

## Подготовка и требования

- Windows PowerShell, Docker Desktop в режиме Linux containers, Docker Compose v2
  с командой `docker-compose`.
- Ориентир для Docker Desktop: не менее 8 ГБ доступной RAM на весь проект;
  12–16 ГБ дают больше запаса. Это рекомендация, фактическое потребление измеряется ниже.
- Модель занимает около 1,9 ГБ; дополнительно нужны место для образа Ollama,
  остальных образов и кэша сборки. Практический запас свободного диска — от 10 ГБ.
- GPU не нужен. Скорость на CPU зависит от процессора и выделенных Docker ресурсов.

Первичная сборка, скачивание образов и `ollama pull` требуют интернета.
После подготовки образов и модели обработка может выполняться без интернета.
Для изолированного стенда подготовьте образы и том `ollama_models` заранее
и перенесите их в контур штатными средствами вашей инфраструктуры.
Профиль Compose сам по себе не блокирует исходящие сетевые подключения:
сетевую изоляцию обеспечивает инфраструктура контура. Здесь используется
локальная модель, а не модель с суффиксом `:cloud`.

## Запуск — команды PowerShell по одной

Откройте PowerShell в корне репозитория. Если `.env` ещё нет:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Соберите приложение и запустите профиль:

```powershell
docker-compose build api
docker-compose --profile local-llm up -d --build
docker-compose --profile local-llm ps
```

Дождитесь состояния `healthy` у Ollama. Оно проверяет доступность сервера,
а не наличие модели. Скачайте модель одной командой:

```powershell
docker-compose exec ollama ollama pull qwen2.5:3b
```

Модель сохраняется в томе `ollama_models:/root/.ollama`, повторное скачивание
после пересоздания контейнера не требуется. Не удаляйте том через `down -v`.

В локальном `.env` **замените** существующие значения этих четырёх переменных
(не добавляйте вторые строки с теми же именами):

```dotenv
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=http://ollama:11434/v1
LLM_API_KEY=ollama
LLM_MODEL=qwen2.5:3b
```

`ollama` — произвольная заглушка в поле ключа; сервер Ollama её игнорирует.
Настоящий API-ключ не нужен. `.env` не коммитьте; в `.env.example` этот блок
остаётся закомментированным, значение по умолчанию — `LLM_PROVIDER=mock`.

Примените настройки к обоим процессам (они читаются при старте):

```powershell
docker-compose up -d --build --force-recreate api worker
docker-compose restart frontend
```

Перезапуск frontend обновляет адрес API в Nginx после пересоздания контейнера.
Если вместо перехода к проверке появляется «Ошибка сервера (502)», выполните
эту команду и повторите отправку. Код frontend менять не требуется.

При необходимости заранее прогрейте модель без текста документа:

```powershell
docker-compose exec ollama ollama run qwen2.5:3b "Ответь одним словом: готово"
```

## Проверка через интерфейс и Swagger

1. Откройте [интерфейс](http://localhost:3000), вкладку «Проверить текст».
2. Выберите назначение «Договор с контрагентом» и вставьте синтетический пример:

   > Заказчик поручает Исполнителю обработку персональных данных работников Заказчика по поручению оператора в соответствии с ч. 3 ст. 6 Федерального закона № 152-ФЗ. Исполнитель принимает необходимые меры для защиты персональных данных в соответствии с законодательством. Ответственный: Сидоров Пётр Ильич, тел. +7 913 555-12-34.

3. Запустите проверку. Обработка идёт в Celery; дождитесь страницы отчёта.
   Скопируйте `report_id` из адреса `/reports/<report_id>`.
4. Откройте [Swagger](http://localhost:8000/docs), раскройте
   `GET /api/reports/{report_id}/llm-log`, нажмите **Try it out**,
   введите `report_id` и нажмите **Execute**.
5. Зафиксируйте для каждой записи `rule_id`, `verdict`, `quote`, `cached`.
   В `masked_fragment` должны быть `[PERSON_1]` и `[PHONE_1]`, исходного ФИО
   и телефона быть не должно. `quote` — дословная цитата из маскированного
   фрагмента либо `null`; ответ `yes` без найденной цитаты понижается до `unknown`.
6. Через `GET /api/reports/{report_id}` запишите `processing_ms`, `llm_used`,
   `audit.llm_provider`, `audit.llm_model`, `audit.llm_calls`.
   Для локальной модели ожидается `openai_compatible` и `qwen2.5:3b` в audit.

Журнал показывает LLM-условия, до которых дошли правила. Пустой журнал не
доказывает работу модели: выбранный документ мог не активировать смысловую проверку.
Успешные ответы кэшируются в Redis на 7 дней. Повторный запрос может иметь
`cached=true`, `audit.llm_calls=0` и `llm_used=false`, хотя журнал содержит
результат ранее выполненной локальной проверки.

Проверить размер модели, размещение на CPU и текущее потребление RAM:

```powershell
docker-compose exec ollama ollama list
docker-compose exec ollama ollama ps
docker stats --no-stream
docker-compose logs --tail 50 worker
```

`ollama list` показывает размер на диске, `ollama ps` — загруженную модель,
её размещение и размер в памяти; `docker stats` — RAM всего контейнера.
По умолчанию модель выгружается из памяти после периода простоя.

## Ограничения и таймауты

На CPU ответы могут приходить медленно, особенно при первом запуске и при
параллельных проверках. Клиент использует таймаут HTTPX на сетевую операцию
`LLM_TIMEOUT_S` (по умолчанию 30 секунд, для CPU — 120; см. «Какую модель выбрать»), до трёх попыток при сетевых ошибках/429/5xx с паузами 1 и 3 секунды.
Это не общий лимит времени документа: несколько условий и окон увеличивают время.
На невалидный JSON предусмотрен один дополнительный запрос с просьбой исправить ответ.

При исчерпании попыток из-за таймаута проверка документа продолжается:
соответствующая запись журнала получает `verdict="unknown"`, `quote=null`.
Нарушение по этому условию не создаётся; проверки регулярными выражениями
и обычными правилами сохраняются. `unknown` означает, что смысловой вывод
получить не удалось, и не означает отсутствие нарушения.

`llm_used` вычисляется по факту списания бюджета реальных вызовов, а не по
успеху ответа: при попытках, закончившихся таймаутом, он может быть `true`.
В mock он `false`; при ответах только из кэша — также `false`.
Отсутствие `LLM_BASE_URL` или `LLM_MODEL` включает безопасный fallback на mock.
Качество небольшой модели требует отдельной оценки и сравнения с облачной.

## Какую модель выбрать (T-029b)

Цифры в таблицах — только из замеров на компьютере команды; до замера — `[заполнить по замеру]`.
Корпус — `eval/seed` (31 синтетический документ; `eval/dev` в репозитории нет).
`eval/blind` для выбора модели не используется: это финальный замер 27.10.

### Что сравнивали

Модели из реестра Ollama (`qwen2.5:3b`) у нас не скачались: файлы весов отдаются с Cloudflare R2,
и соединение рвалось (`server gave HTTP response to HTTPS client`). Поэтому те же веса
Qwen2.5-Instruct в том же квантовании Q4_K_M взяты с Hugging Face (`hf.co/...`).

| Модель | Почему в списке | Размер (`ollama list`) |
|---|---|---|
| `hf.co/bartowski/Qwen2.5-3B-Instruct-GGUF:Q4_K_M` | модель T-029 (`qwen2.5:3b`), самая быстрая | 1,9 ГБ |
| `hf.co/bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M` | та же семья, больше параметров: сколько качества даёт размер | 4,7 ГБ |
| `hf.co/t-tech/T-lite-it-2.1-GGUF:Q4_K_M` | 8B на базе Qwen3, дообучена на русском (Т-Банк), Apache-2.0: даёт ли русское дообучение больше, чем размер | 5,0 ГБ |
| облачная модель из `.env` (`gpt-4o-mini`) | базовая линия: что теряем при переходе в контур | — |

### Важно: как читать метрики

В обычном режиме (`compare_models.py` без флагов) на `eval/seed` у всех моделей, включая облако,
одинаковые метрики: recall SPECIAL_CATEGORY и TRADE_SECRET = 1.000. Эти типы на seed уже находят
словари и регулярные выражения, и нейросети нечего добавить. Поэтому модели сравниваются в режиме
`--semantic-only`: находки SPECIAL_CATEGORY и TRADE_SECRET от словарей убираются, и эти типы ищет
только нейросеть. Recall в этом режиме — **вклад самой модели**, а не итог системы.

### Рекомендация (решение тимлида 24.10: два профиля)

Исходное правило — лучшее качество при ≤ 60 с на документ на CPU. Его формально проходит
только 3B (30,7 с), но вклад 3B почти нулевой (0 из 12 особых категорий, 1–3 из 25 КТ).
7B на CPU превышает порог на 10 % (66,5 с), зато находит около половины того, что облако.
Поэтому два профиля:

| Профиль | Модель (`LLM_MODEL`) | Время на документ | Вклад модели SPEC / КТ | Когда |
|---|---|---|---|---|
| **CPU** (по умолчанию, `.env.example`) | `hf.co/bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M` | 66,5 с (макс. 116 с) | 0.42 / 0.48 | нет видеокарты NVIDIA; RAM для ollama ≥ 6 ГБ |
| **GPU** | `hf.co/t-tech/T-lite-it-2.1-GGUF:Q4_K_M` | 33 с в среднем из-за двух зависаний (остальные — единицы секунд) | 0.58 / 0.60 | NVIDIA ≥ 8 ГБ VRAM; пока не устранены зависания — либо 7B на GPU (1,9 с/док) |

В обоих профилях `LLM_TIMEOUT_S=120`. 3B не рекомендуем: время в норме, но смысловую
проверку она почти не выполняет — в контуре на ней держались бы только словари.

Что теряется по сравнению с облаком (gpt-4o-mini: 0.75 / 0.64): у 7B — примерно половина
смысловых находок облака, у T-lite — около 90 % по коммерческой тайне и около 80 % по особым
категориям. Пропуски облака и T-lite в основном одни и те же (`12_kalkulyaciya`,
`27_anketa_komissiya`, `28_kalkulyaciya_lot3`) — вероятно, дело не в модели; разбор вынесен
в отчёт T-029b как открытый вопрос. Итог системы на seed со словарями — 1.000 в любом профиле.

Скачать модель профиля (из реестра Ollama `qwen2.5:*` у нас не скачивается, см. выше):

```powershell
docker-compose exec ollama ollama pull hf.co/bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M
```

Почему переход в контур безопасен, даже если локальная модель слабее. Ответ любой модели —
облачной или локальной — проходит одну и ту же проверку кодом: находка принимается, только
если её цитата дословно есть в отправленном фрагменте (`quotes.py`, `checks.py`); ответ «yes»
без цитаты понижается до `unknown`. Слабая модель может **пропустить** находку, но не может
**выдумать** её. Поэтому замена модели меняет только полноту, и полноту мы измерили выше.
Регулярные выражения, словари и NER работают без нейросети и от модели не зависят.

### Память и таймаут

- Ориентир RAM контейнера `ollama`: размер модели на диске + 0,5–1 ГБ на контекст и сервер.
  Фактический пик — столбец «RAM ollama» выше (`docker stats`).
- `LLM_TIMEOUT_S` — таймаут **одного** HTTP-запроса (секунды, по умолчанию 30). На CPU ответ
  приходит целиком после генерации, поэтому ставьте 120. При таймауте клиент повторяет запрос
  до 3 раз (паузы 1 и 3 с), так что худший случай на один вызов — `3 × LLM_TIMEOUT_S + 4` с;
  число вызовов на документ ограничено `LLM_MAX_CALLS_PER_DOC`. После исчерпания попыток
  проверка не падает: запись журнала получает `verdict="unknown"`.
- Контекст. Ollama на CPU по умолчанию выделяет 4096 токенов и молча обрезает начало длинного
  запроса (а там системный промпт). Скрипт сравнения печатает предупреждение, если
  `max total_tokens` ≥ 3686. Тогда раскомментируйте в `docker-compose.yml` у сервиса `ollama`
  строку `OLLAMA_CONTEXT_LENGTH=8192`, пересоздайте сервис и проверьте столбец `CONTEXT`
  в `docker-compose exec ollama ollama ps`. Больше контекст — больше RAM.

### Как включить GPU (NVIDIA)

По умолчанию модель работает на CPU. Если на компьютере есть видеокарта NVIDIA с актуальным
драйвером и Docker Desktop работает на WSL2:

1. подключите docker-compose.gpu.yml (см. комментарий в файле)
2. Пересоздайте сервис: `docker-compose --profile local-llm up -d --force-recreate ollama`.
3. Сделайте один запрос (прогрев выше) и выполните `docker-compose exec ollama ollama ps`:
   в столбце `PROCESSOR` должно быть `100% GPU` (или доля GPU/CPU, если модель не поместилась).

Без NVIDIA блок оставляйте закомментированным: на компьютере без GPU контейнер с этим
блоком не запустится. Коммитить раскомментированный блок нельзя — у жюри может не быть GPU.

### Как повторить замер

Скрипт `eval/compare_models.py` (T-029b) прогоняет корпус каждой моделью тем же детектором,
что `run_eval.py --llm`, и пишет `compare.json` и `metrics.json`/`errors.json` по моделям.
Команды по одной — в отчёте T-029b; основная:

```powershell
docker-compose run --rm -e LLM_PROVIDER=openai_compatible -e LLM_BASE_URL=http://ollama:11434/v1 -e LLM_API_KEY=ollama -e LLM_TIMEOUT_S=120 -v "${PWD}/eval:/eval" -v "${PWD}/eval/results:/out" api python /eval/compare_models.py --corpus /eval/seed --models hf.co/bartowski/Qwen2.5-7B-Instruct-GGUF:Q4_K_M --out /out/sem-qwen7b --no-cache --semantic-only
```

Без `--semantic-only` — итог системы (словари + нейросеть), с ним — вклад одной модели.

`/out`, а не `/eval/results`: у сервиса `api` папка `eval/results` смонтирована только для чтения.

## Возврат к mock

В `.env` установите `LLM_PROVIDER=mock`. Остальные три локальные настройки
можно оставить: mock их не использует. Пересоздайте API и worker, затем
остановите Ollama:

```powershell
docker-compose up -d --build --force-recreate api worker
docker-compose restart frontend
docker-compose --profile local-llm stop ollama
docker-compose up --build -d
docker-compose ps
```

В последнем выводе среди работающих сервисов Ollama быть не должно.
Профиль управляет запуском, но **не останавливает уже запущенный контейнер**:
одной команды `up` без профиля для остановки Ollama недостаточно.
Модели остаются на диске для следующего запуска профиля.
