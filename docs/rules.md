# Каталог правил проверки

Человекочитаемое описание правил из `data/rules/rules.yaml`. Ведёт **Алина**.
Каждое правило здесь — одна запись в YAML с тем же ID (формат условий — `docs/contracts.md`, раздел 2).

Уровень: **red** — серьёзное нарушение, документ нельзя отправлять как есть;
**yellow** — замечание, стоит исправить.

Обозначения в столбце «Когда срабатывает»:
- **назначение** — `internal` «внутренний», `publication` «для публикации», `contract` «договор с контрагентом», `international` «международный контракт»;
- **найдены данные** — типы сущностей из контракта (PERSON, PASSPORT, SNILS, INN, PHONE, EMAIL, ADDRESS, BIRTH_DATE, CARD, BANK_ACCOUNT, SPECIAL_CATEGORY, TRADE_SECRET);
- **маркер** — есть или нет в документе: лист согласования, гриф, срок хранения, согласие на обработку ПДн, условия поручения обработки, упоминание КИИ;
- **Вопрос ИИ** — проверка смысла нейросетью по замаскированному тексту. Нарушение — только если ИИ ответил **«да»**. Без ключа LLM такие правила не срабатывают и не создают ложных нарушений.

## Как добавить правило

1. Добавьте строку в таблицу выше.
2. Добавьте запись в `data/rules/rules.yaml` с тем же ID.
3. Запустите `cd backend && pytest tests/test_schemas.py` — правило должно пройти валидацию.

## Принципы составления правил

- У каждого нарушения есть пункт регламента: статья закона или «Внутренняя политика».
- Правила не должны срабатывать на каждом документе. ФИО и телефон подписантов есть почти в любом договоре, поэтому чек-листовые правила опираются на «тяжёлые» ПДн — паспорт, СНИЛС, ИНН физлица, дату рождения. Финансовые данные (реквизиты организаций) коммерческой тайной не считаются.
- Вопрос ИИ формулируется так, чтобы ответ «да» означал нарушение. Конструкция «НЕ + вопрос ИИ» не используется: без ключа LLM она дала бы ложное срабатывание.
